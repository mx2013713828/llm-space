# LLM-Space Development Spec & Philosophy

> This document is not just a coding standard; it embodies the core philosophy refined through our process of building, troubleshooting, and refactoring LLM-Space. Any new feature development or architectural adjustment must first align with this guide.

## I. Core Philosophy

### 1. Transparency & User Control — No Black Box Magic
- **What You See Is What You Get (WYSIWYG)**: The underlying Harness must never mutate core data (such as rearranging the System Prompt) using fragile heuristics (e.g., regex extraction or intent guessing) without the user's knowledge.
- **Return Control to the User**: Advanced optimizations (like Prompt Cache alignment) should be achieved through explicit tag guidance or by letting the user format it themselves. The role of the Harness is to faithfully transmit instructions and provide infrastructure, not to overstep and make "smart" decisions for the user.

### 2. Progressive Complexity — Maintain the Sandbox Nature
- **Feature Decoupling**: LLM-Space is essentially an Agent architecture laboratory. All bleeding-edge Harness mechanisms (concurrent tool execution, hardcore context compaction, chain-of-thought injection) must be **pluggable configurations (Feature Flags)**.
- **From Simple to Complex**: Allow users to start with a minimalist ReAct loop. When bottlenecks are encountered, they can toggle switches to experience the architectural upgrades. Do not impose extreme complexity on simple tasks.

### 3. Extreme Defensive Design — Built for Chaos
- **Anti-Crash Baseline**: The output of LLMs is inherently unreliable and hallucination-prone (e.g., fabricating an Array into a Number), and network connections can drop at any time.
- **Defense in Depth**: From backend API request parsing and streaming tool execution (`try-catch` everything) to frontend React state rendering, every layer must perform mandatory type conversions and defensive checks (like `Array.isArray` fallbacks) when receiving external data to ensure a single failed call doesn't crash the entire loop process.

## II. Context & Memory Engineering

> The capability boundary of an LLM is determined by its attention mechanism. Context engineering is the core moat of the Harness.

### 1. Cache-First Architecture
When assembling the API Payload for the LLM, the **"Static First, Dynamic Last"** principle must be strictly followed to maximize Anthropic/DeepSeek prefix caching:
- **Static Zone (Front)**: Place massive, rarely changing elements like the System Prompt, role definitions, and full tool schemas here.
- **Dynamic Zone (Back)**: Place rapidly changing elements like the current time, dynamic directories, and the task board state (`<current_tasks_status>`) at the very end of the Payload.

### 2. Memory Overflow Defense (Three Lines of Defense)
Long-running tasks must never blow up the Context Window:
- **1st Line of Defense (Physical Offload)**: Except for `read_file` (which requires the model to read the whole file), all other tools that output data exceeding a specific threshold (e.g., 20KB) must be forcibly intercepted and written to disk, returning only a head/tail summary to the context.
- **2nd Line of Defense (Soft Compact)**: When Tokens reach a dangerous watermark (e.g., 80%), dynamically fold outdated tool returns (like old terminal outputs or past file writes) to free space while keeping the conversation timeline intact.
- **3rd Line of Defense (Hard Compact / Epoch)**: When the system is on the verge of collapse, back up the full physical logs, silently spin up a background summarization task to condense tens of thousands of words into a brief battle report, clear the upstream context, and inaugurate a new epoch.

### 3. Maintain Mainline Purity (Sub-agent Delegation)
The garbage context generated by complex, long-term exploration and trial-and-error will severely pollute the main model's judgment.
- Divergent research should be forcibly delegated to a `sub_agent`.
- Only the "final refined summary" returned by the sub-agent should be kept in the main model's context.

### 4. Three-Layer Guidance and Memory System
Long-term context must be layered so explicit rules, uncertain observations, and durable facts do not collapse into one opaque memory bucket:
- **Explicit Guidance Layer**: Rules, project conventions, and durable user instructions that the user explicitly wants the agent to follow. This layer is file-backed through editable `AGENTS.md` files and is not automatic memory.
- **Auto-Capture Working Layer**: Automatically extracted memory first lands in a candidate/working layer. This layer may contain uncertain, provisional, or potentially stale information, but it should not interrupt the main chat flow by default.
- **Curated Long-term Layer**: Only high-confidence, stable, cross-session information should be written into long-term memory. Sensitive information must fail closed. One-off teammate reports, transient review outputs, and runtime noise should be discarded or kept in observable queues instead.

### 5. Context Inspector as Payload Inspector
The Context Inspector is not a general runtime dashboard. Its job is to clearly and completely show what the current model request actually receives:
- By default, it should show only **System Prompt sections, Messages Payload, and Provider Tool Schema**.
- Runtime queues, memory candidates, and tool-pool summaries belong in separate observability surfaces unless they are actually injected into the model request.
- `Messages Payload` must support continuous transcript reading instead of forcing one-message-at-a-time inspection. `thinking`, `tool_use`, and `tool_result` blocks need visually distinct treatment.
- Dynamic execution strategy guidelines should be pinned into the System Prompt assembly layer instead of appended to the latest user turn on every request. This protects prompt cache behavior and makes context easier to reason about.

### 6. Knowledge Bases and Mountable Resources
External knowledge bases, skills, project documents, and future MCP resources should be treated as mountable resources, not hard-coded prompt text:
- Users should be able to upload/generate knowledge bases and explicitly mount them in a conversation.
- Model injection must be bounded and source-labeled. For example, `<mounted_knowledge>` should include only retrieved, limited snippets.
- Large file contents must not be pushed directly into trajectory or messages. They should enter context through indexing, retrieval, and traceable citations.
- Knowledge mounting should reuse the Context Inspector prompt assembly mechanism so users can see exactly which knowledge snippets were injected.

## III. State Sync & Network

### 1. Break the Sync Cycle
In the state synchronization between the React frontend and the backend/persistence layer, a "ping-pong effect" is highly likely (e.g., passive sync triggers active upload, active upload changes global state, global state triggers passive sync again).
- **Solution**: State transitions must have a clear **Source of Truth**. When passively receiving backend state syncs, use a `Ref` pre-fill marker to intercept the frontend from broadcasting it back as a "new input", physically cutting off the feedback loop.

### 2. Background-First Lifecycle
The physical lifecycle of the Agent is decoupled from the frontend page lifecycle.
- **Frontend as a Monitor**: The ReAct loop of the Harness lives independently in the backend `AgentExecutor`.
- **Disconnect Immunity**: If the user closes the browser or refreshes the page, the Agent must continue running silently in the background. When reopened, the frontend should actively query `/api/agent/status` via the `harnessId` and automatically Attach to the SSE stream to seamlessly resume the scene.

## IV. Tools & Skills

### 1. On-Demand Progressive Discovery
- **Farewell to Bloat**: Whether the system integrates 100 or 1000 professional skill guides, **never** stuff their full text into the System Prompt.
- **Dynamic Addressing**: Expose only the skill names, brief descriptions, and their corresponding Markdown file paths in the Prompt. Let the LLM autonomously use the `read_file` tool to fetch the detailed guide on-demand, achieving zero-overhead cold starts.

### 2. Fail-Closed Permission Control
- Any tool capable of modifying the physical disk or executing system commands is dangerous by design.
- In future evolutions, for high-risk operations (like `bash`), the Harness must have the ability to suspend execution and mandate `Manual Review` from the user, locking the blast radius within the sandbox.

### 3. Provider-Neutral Model Gateway
The Agent Loop should not care whether the underlying model comes from Anthropic, OpenAI, DeepSeek, Kimi, GLM, MiniMax, or another provider:
- Internally, the Harness should use provider-neutral runtime events and message/tool representations.
- Protocol adapters are responsible for converting internal messages, tools, thinking/reasoning, usage, and prompt-cache fields into the provider API format.
- The same third-party provider may use either the `anthropic` or `openai_chat_completions` protocol depending on actual API support. `baseUrl`, `protocol`, `extraBody`, and provider hints belong to model configuration, not Agent Loop branching.
- Provider-specific parameters may enter the gateway through controlled `extraBody`, but they must not overwrite core fields or bypass security/tool-dispatch protocols.

## V. Coding & Architecture Specs

### 1. Modular & Detachable
- **High Cohesion, Low Coupling**: Newly added Harness features (like context compaction, sub-agent management, state persistence) must be encapsulated in independent functions or modules (e.g., pure functions in `messageBuilder.js`) to avoid piling thousands of lines of logic into the `AgentExecutor` class.
- **Pure Functions Preferred**: Logic like Token estimation, Payload assembly, and soft compaction must be designed as zero-side-effect **Pure Functions**, facilitating independent unit testing and preventing accidental state pollution.
- **Feature Flags**: Any new feature altering core execution logic must initially be controlled via `features.xxx_enabled` flags to ensure the code falls back 100% to the classic ReAct path if turned off.

### 2. Hook-Based Agent Loop Architecture (Lifecycle Spec)
Referencing mature industry Agent design philosophies (like Claude Code), when inserting new features or functions into the `AgentExecutor` main loop (ReAct Loop), a Hook-based flow must be strictly followed. 
We must avoid piling `if-else` blocks in the main loop; future extensions should follow this standardized execution pipeline:

1. **`UserPromptSubmit` (User Input Handling)**:
   - Purpose: Record, inject, and audit user input.
   - Timing: Before the loop starts. Examples: initial Token checks, runaway prevention.

2. **`PreLLM / State Assembly` (Before LLM Call)**:
   - Purpose: Assemble context and memory.
   - Mechanisms:
     - **cron / background**: Inject background task completion notifications (`<task_notification>`).
     - **Compaction**: Trigger soft context wash (Soft Compact) or epoch reconstruction (Hard Compact).
     - **Prompt Builder**: Static/dynamic separation, inject on-demand Skills list, merge `todos` board state (`<current_tasks_status>`).

3. **`LLM Call` (Network Request Layer)**:
   - Purpose: Initiate model request, handle timeouts, 502 retries, Fallback downgrades.
   - Error Recovery: If a request fails, it shouldn't crash directly; instead, log the Error Message and end the current turn, waiting for human intervention or automatic retry.

4. **`PreToolUse` (Pre-Execution Defense)**:
   - Purpose: Interception and permission auditing.
   - Mechanisms: Upon parsing a `tool_use` block, verify if it's a dangerous command here. Unauthorized writes or high-risk Bash can be suspended here, requesting `Manual Review` from the frontend.

5. **`Tool Dispatch` (Tool Dispatch & Execution)**:
   - Purpose: Actual physical layer execution.
   - Mechanisms: Concurrent dispatch (based on `features.parallel_tool_execution`), or dispatching slow Bash tasks to a background daemon thread while the main loop returns a placeholder result.

6. **`PostToolUse` (Post-Execution Processing)**:
   - Purpose: Result auditing and persistence.
   - Mechanisms: Automatic physical truncation and Offload of massive text outputs, real-time `tool_exec_done` broadcasts to the frontend.

7. **`Stop` (Loop Exit)**:
   - Purpose: Statistics, cleanup, and state settlement.
   - Mechanisms: If there is no `tool_use` this round (pure text model output), trigger `saveSession` persistence and broadcast the end of the round to the frontend, awaiting the next user input.

### 3. Before adding new plugins or features, their location in the Agent Loop must be reviewed with the user.

### 4. Task Orchestration Must Stay Detachable and Experimental
LLM-Space is an experimental platform and should not fully black-box commercial-Agent-style "smart execution modes":
- `write_todo`, DAG `task-system`, `sub_agent`, `async teams`, reviewer/verifier, and related primitives are detachable lower-level components.
- "Inline Execution", "Sequential Sub-agent Workflow", and "Async Agent Teams" should be higher-level strategy presets that compose these primitives while still allowing users to switch components independently.
- Simple tasks should not be over-orchestrated. When the user explicitly requests a specific execution method (for example, "call sub-agent"), the Harness should respect it unless it first confirms a better alternative with the user.
- child agents, sub-agents, and teammates should reuse the same permission approval, tool safety, trajectory summary, and result reliability protocols instead of each implementing temporary one-off logic.
